## Обзор 🎯
Управление файловыми вложениями к тест-кейсам, планам, результатам и прогонам.
Поддерживаемые типы ресурсов для прикрепления файлов:

> [!TIP]
> Для быстрого старта по `attachments`: проверьте `--help`, затем выполните
> безопасный/проверочный запуск перед боевым сценарием.

## Синтаксис 🧩
```bash
gotr attachments [command]
```

## Подкоманды

| Подкоманда | Описание |
| --- | --- |
| `add` | Добавить вложение к ресурсу |
| `list` | Показать вложения для case, plan, plan-entry, project, run и test |
| `cleanup` | Массовое удаление старых вложений со снапшотом и возможностью отката |

### ▶️ Сценарий 6: Массовая очистка старых вложений (со снапшотом и откатом)

🎯 **Цель:** освободить место, удалив вложения старше заданной границы, сохранив возможность отката.

```bash
# Только предпросмотр — список кандидатов по проектам, без снапшота и без удаления.
gotr attachments cleanup --all-projects --older-than 90d --dry-run

# Реальная очистка вложений у результатов старше 3 месяцев по всем
# видимым проектам. Снапшот создаётся автоматически и хранится 7 дней
# (категория `cleanup-attachments`, TTL по умолчанию).
gotr attachments cleanup --all-projects --older-than 3M --entity-type result

# Только конкретные проекты, повышенный параллелизм, без снапшота
# (НЕ рекомендуется вне одноразовых окружений).
gotr attachments cleanup --project 7,9 --older-than 30d --concurrency 8 --no-snapshot --force
```

**Ключевые флаги:**

| Флаг | Назначение |
| --- | --- |
| `--project <ids>` / `--all-projects` | Обязательный селектор охвата (взаимоисключающие). |
| `--older-than <dur>` | Граница возраста (`7d`, `3M`, `1y`, `720h`). Обязателен, если не задан `--dry-run`. |
| `--entity-type` | Фильтр по родителю: `case`, `run`, `plan`, `plan_entry`, `result`, `test`. **Дефолт с v3.5.2: все шесть типов.** Если итоговый scope покрывает ВСЕ типы, перед сканированием в stderr печатается ⚠️ предупреждение; для суженного scope — однострочное `ℹ️`. Чтобы сузить обход, передайте явный список (например, `--entity-type result`). |
| `--dry-run` | Только предпросмотр, без снапшота и удалений. |
| `--no-snapshot` | Отключить страховочный снапшот. |
| `--snapshot-retention <dur>` | Переопределить TTL снапшота (по умолчанию `7d`; учитывается в `gotr snap gc`). |
| `--max-size-gb <n>` | Прервать запуск, если оценка размера снапшота больше указанного значения (если не задан `--force`). |
| `--concurrency <n>` | Количество параллельных воркеров удаления (по умолчанию `4`). |
| `--backup-concurrency <n>` | Воркеры скачивания снапшота (по умолчанию `0` = авто: `min(8, --concurrency)`). С v3.6.0. |
| `--skip-references` | Отключить сканирование markdown-ссылок при бэкапе. Ссылки на удаляемые вложения не будут переписаны при откате. С v3.6.0. |
| `--limit <n>` | Ограничение общего числа обрабатываемых вложений по всем проектам. |
| `--scan-strategy` | Стратегия перечисления вложений: `auto` (по умолчанию), `project`, `entities`. См. раздел **Совместимость** ниже. |
| `--chunk-size <n>` | Сколько проектов сканируется в одном чанке; чекпойнт записывается атомарно после каждого чанка. По умолчанию `10`. См. раздел **Восстановление и resume** ниже. |
| `--scan-timeout-per-project <dur>` | Таймаут сканирования одного проекта (по умолчанию `10m`). При срабатывании проект помечается `timeout` в чекпойнте, запуск продолжается; resume повторит его. Передайте `0`, чтобы отключить. |
| `--resume <RUN_ID>` | Возобновить прерванный запуск из чекпойнта. Несовместим с флагами scope/фильтра — они восстанавливаются из чекпойнта. |
| `--list-checkpoints` | Вывести таблицу всех чекпойнтов и завершить работу. Несовместим с любыми другими флагами. |
| `--no-report` | Не записывать аудит-отчёт об удалении (Markdown + JSON + CSV + PDF). См. раздел **Аудит-отчёт об удалении** ниже. |
| `--force` | Пропустить финальный запрос подтверждения. |

**🧭 Совместимость (TestRail Server vs Cloud):**

Эндпоинт `get_attachments_for_project` появился в **TestRail 7.5**. Более старые self-hosted установки (TestRail Server &lt; 7.5) отвечают `404 Unknown method`. Чтобы поддержать оба варианта, `gotr` использует **две стратегии сканирования**:

| Стратегия | Как перечисляются вложения | Работает на |
| --- | --- | --- |
| `project` | Один bulk-вызов `get_attachments_for_project`. | TestRail 7.5+ / Cloud |
| `entities` | Обход `get_suites → get_cases → get_attachments_for_case`; плюс (если разрешено `--entity-type`) `get_runs → get_attachments_for_run`, `get_plans → get_attachments_for_plan` + по entry `get_attachments_for_plan_entry`, и `get_runs → get_tests → get_attachments_for_test` (единственный путь к result-bound вложениям на Server &lt; 7.5). Результаты дедуплицируются по ID вложения. | TestRail 5.7+ |
| `auto` (по умолчанию) | Один пробный вызов project-эндпоинта на первом проекте; переключение на `entities` происходит **только** при канонической ошибке `404 Unknown method`. Любая другая ошибка прерывает запуск — без молчаливого fallback. | оба варианта |

При срабатывании fallback в stderr выводится строка `INFO:` с причиной переключения. В CI и неинтерактивных сценариях стратегию можно зафиксировать явно: `--scan-strategy=entities` или `--scan-strategy=project` — это полностью отключает probe-вызов.

**Откат:** снапшот сохраняется под категорией `cleanup-attachments` и восстанавливается стандартным потоком snap:

```bash
gotr snap list --category cleanup-attachments
gotr snap rollback <snap-id>

# Проверить SHA-256 каждого файла снапшота перед откатом (с v3.6.0).
gotr snap rollback <snap-id> --verify-integrity

# Пропустить шаг переписывания markdown-ссылок (с v3.6.0).
gotr snap rollback <snap-id> --skip-references
```

⚠️ В TestRail API нет endpoint `add_attachment_to_test`, поэтому вложения, родителем которых является только `test`, при откате помечаются как **Skipped** — учитывайте это, если такие вложения важны.

**🔐 Полнота снапшота (с v3.6.0):**

Каждый снапшот cleanup теперь содержит артефакты, необходимые для полного отката удаления, включая аудит-индекс markdown-текстов, ссылавшихся на удалённые бинарники:

```
<snap_id>/
├── meta.json            # метаданные снапшота
├── attachments.json     # v2 ledger: SHA-256 + флаг restorable + поле new_id на каждое вложение
├── references.json      # аудит-индекс markdown-URL'ов в других сущностях, ссылавшихся на удалённые вложения
├── integrity.json       # SHA-256 на файл + merkle-style root по всему снапшоту
└── files/<id>(.gz)      # двоичные данные, опционально gzip-сжатые
```

- **`attachments.json`** содержит запись на каждое вложение: исходный ID, SHA-256 файла на диске, родительская сущность, флаг `restorable` (`false` для test-bound вложений, поскольку TestRail не имеет endpoint `add_attachment_to_test`) и поле `new_id`, заполняемое при rollback'е новым ID, выданным TestRail.
- **`references.json`** — аудит-индекс всех markdown-URL'ов, ссылающихся на удаляемые вложения. Сканируются поля описаний `case`, `run`, `plan`, `milestone` плюс `case.custom_steps_separated`. **В v3.6.0 индекс только записывается; тела внешних сущностей НЕ модифицируются** — ни на cleanup, ни на rollback. После cleanup ссылки вида `[label](.../attachments/get/<old_id>)` в других сущностях вернут 404; после rollback вложения восстановятся под **новыми** TestRail ID, и старые ссылки останутся битыми. Ручная переписка возможна по сохранённому индексу. Автоматическая переписка — на roadmap (отложена из v3.6.0 из-за риска read-modify-write race на разделяемых сущностях TestRail).
- **`integrity.json`** содержит SHA-256 каждого файла снапшота и merkle-style root, считаемый по отсортированным строкам `<path>|<sha256>`. Передайте `--verify-integrity` в `gotr snap rollback`, чтобы выполнить сверку до любого API-вызова.
- Скачивание бинарников при бэкапе распараллелено через `--backup-concurrency`; SHA-256 считается на лету, без второго прохода.

**⚠️ Известные ограничения cleanup + rollback (v3.6.0):**

Даже после успешного rollback с `--verify-integrity` восстановленное состояние **не байт-в-байт** идентично тому, что было до cleanup. API TestRail вынуждает следующие отличия:

| Поле | До cleanup | После rollback | Причина |
| --- | --- | --- | --- |
| `attachment_id` | исходный | **новый** (мапится в `attachments.json` через `new_id`) | `add_attachment_to_*` всегда выдаёт свежий ID |
| `created_on` | исходное время | **время выполнения rollback** | API не принимает back-dated значение |
| `created_by` | исходный загрузчик | **API-пользователь, выполняющий rollback** | API не принимает back-dated пользователя |
| URL | `.../attachments/get/<old_id>` | `.../attachments/get/<new_id>` | следствие нового ID |
| Markdown-ссылки в ДРУГИХ сущностях | указывали на `<old_id>` | **по-прежнему указывают на `<old_id>` → 404** | gotr не модифицирует внешние сущности; см. `references.json` |
| Test-bound вложения | присутствовали | **пропускаются** | нет endpoint `add_attachment_to_test` |

Практические следствия:

- Для аудита/комплаенса, опирающихся на исходные `created_on`/`created_by`, рассматривайте rollback как инструмент **восстановления контента**, а не машину времени.
- Для целостности markdown в телах case/run/plan/milestone используйте `references.json` из снапшота для ручной или скриптовой переписки. Аудит-отчёт об удалении содержит секцию `Known limitations: markdown references` с разбивкой по типам сущностей.
- Если битые внешние ссылки неприемлемы — лучше использовать `--dry-run` и ручной архив вместо `cleanup` для соответствующих проектов до выхода автоматической переписки.

**📑 Аудит-отчёт об удалении (с v3.5.1):**

Каждый запуск `attachments cleanup` — включая `--dry-run` — автоматически записывает аудит-отчёт по пути:

```
~/.gotr/reports/cleanup-attachments/<label>/<YYYY-MM>/cleanup-attachments-<UTC-timestamp>-<snapshot-id>.<ext>
```

В четырёх форматах одновременно:

| Формат | Назначение |
| --- | --- |
| `.md` | Просмотр человеком. Содержит шапку запуска, применённые фильтры, сводку, разбивку по проектам, полный список удалённых вложений и команду отката. |
| `.json` | Машинная обработка / аудит-пайплайны. Стабильная схема (`internal/report/cleanup.Report`). |
| `.csv` | Просмотр в таблице по каждому удалённому вложению (`project_id, attachment_id, name, size_bytes, parent_kind, parent_id, created_unix, deleted, dry_run, snapshot_id, …`). |
| `.pdf` | Самодостаточный артефакт для передачи (NotoSans встроены). |

`INDEX.md` в корне отчётов перегенерируется после каждого запуска.

Dry-run отчёты содержат маркер `DRY-RUN` в шапке Markdown и `dry_run=true,deleted=false` в строках CSV — их нельзя спутать с реальным артефактом.

Чтобы полностью отключить запись четырёх файлов — используйте `--no-report` (полезно в CI, который и так пишет stdout).

✅ **Что это даёт:** массовое удаление без снапшота — необратимая операция. По умолчанию у вас есть неделя на откат до автоматической очистки снапшота сборщиком мусора.

**🔁 Восстановление и resume (с v3.6.0):**

Долгие entity-walk сканирования по множеству проектов могут прерваться (сетевые ошибки, Ctrl-C, перезагрузка). Чтобы такие запуски были восстанавливаемыми, `cleanup` разбивает множество проектов на чанки и сохраняет прогресс между чанками:

- **Run id:** каждому запуску присваивается стабильный идентификатор (например, `20260324T204109-3f9a12`); он печатается один раз при старте: `INFO: cleanup run-id=<RUN_ID> (resume with --resume <RUN_ID>)`.
- **Расположение чекпойнта:** `~/.gotr/cache/cleanup-attachments/<RUN_ID>/checkpoint.json` плюс `partial-plan.json`.
- **Чанки:** проекты обрабатываются группами по `--chunk-size` (по умолчанию `10`). После каждого чанка оба файла перезаписываются через `tmp + fsync + rename` (атомарно, безопасно к падениям).
- **Per-project таймаут:** `--scan-timeout-per-project` (по умолчанию `10m`) ограничивает сканирование одного проекта. Проекты с таймаутом или ошибкой записываются в чекпойнт и пропускаются в плане, но запуск продолжается.
- **Чистое завершение:** когда все проекты в состоянии `done`, директория чекпойнта удаляется автоматически. Иначе она сохраняется, а в stderr выводится `WARN:` со списком затронутых project id.
- **Просмотр чекпойнтов:** `gotr attachments cleanup --list-checkpoints` выводит таблицу (RUN_ID, started, updated, totals, done, pending, failed, timeout) и подсказку для resume.
- **Возобновление:** `gotr attachments cleanup --resume <RUN_ID>` восстанавливает scope, фильтры, scan strategy, limit и chunk size из чекпойнта и повторяет только проекты в состоянии `pending`/`retry_pending`. Команда отклоняет несовместимые scope/filter флаги — изменить cutoff или scope можно только новым запуском.

> Запуск `--resume` обязан совпадать с исходным фильтром. Если сохранённый `FilterSnapshot` не совпадает с тем, что построил CLI, запуск аварийно завершается с ошибкой `checkpoint mismatch`, а не молча смешивает два фильтра.

**📊 Отчётность о прогрессе (начиная с v3.6.1):**

На фазе сканирования в stderr выводится 5-строчный «живой» блок (если stderr — TTY и не указан `--quiet`):

```
Scanning attachments — entity
   project 4/12  →  Demo project
   phase: cases      ████░░░░░░ 28 / 70
   found: 137  eligible: 89  size: 24.50 MiB
   ⏱ 1m12s  ETA ~3m05s
```

- **Фазы:** `project → suites → cases → runs → plans → tests`. У каждой фазы свой счётчик done/total и 10-символьный бар; общее количество берётся из ответов API (число сьютов, кейсов по сьюту, ранов, планов, тестов на ран).
- **Тротлинг:** события прогресса агрегируются раз в ~50 мс, чтобы не тормозить сканер при высоком уровне параллелизма.
- **Не-TTY / `--quiet`:** многострочный UI отключается, вместо него печатаются строки вида `INFO: project X/Y done: …` и `INFO: chunk N/M done — running totals: …` — удобно грепать в CI-логах.
- **Таблица «проект × тип сущности»:** после выполнения удаления печатается раздел `Breakdown by project × entity type:` со строкой на каждый проект и столбцами по типам (`case run plan plan_entry result test`), а также `Total`/`Size` по строке и итоговая строка футера.
- **Финальный блок:** в разделе `Final summary:` выводятся абсолютные пути всех файлов audit-отчёта, snapshot id и абсолютный путь до `~/.gotr/snaps/cleanup-attachments/<id>/`, а в блоке `Next steps:` — готовые команды для отката (`gotr snap rollback <id>`) и возобновления (`gotr attachments cleanup --resume <run-id>`).

  > ↪️ **Ответ:** когда задача относится к домену этой команды и вы хотите сохранить предсказуемый сценарий работы без смешивания с другими ресурсами.

## 🧾 Ожидаемый результат выполнения

### Что считается успешным результатом

- Команда завершается с кодом `0` и подтверждает применение операции к целевому ресурсу.
- Состояние объекта в TestRail соответствует переданным параметрам после выполнения.
- Повторный `get/list` по целевому ID отражает ожидаемое изменение.

### Практическая проверка результата

- После операции выполните `get`/`list` для того же ресурса и убедитесь, что поля изменились ожидаемо.


---

## 🔎 Проверка результата через соседние команды

- После выполнения команды сделайте соседнюю проверку через `get/list` для того же ресурса.

```bash
# выполнить основную операцию
gotr <command> ...

# проверить результат
gotr get <resource> <id>  # или gotr list <resource>
```

## Практические советы 🧭

- ✅ **Совет: Фиксируйте шаблонные команды**
  > Храните типовые команды для проекта/сьюта/кейса в отдельном internal runbook, чтобы сократить ручные ошибки при повторных запусках.
  >
  > ---

- ✅ **Совет: Логируйте контекст запуска**
  > Перед выполнением сохраняйте ключевые параметры: идентификаторы, URL, выбранные флаги и время запуска. Это ускоряет разбор инцидентов.
  >
  > ---

- ✅ **Совет: Разделяйте диагностический и рабочий режим**
  > Сначала проверка (`--help`, безопасные флаги), затем боевой запуск. Такой режим уменьшает риск некорректных изменений в TestRail.

## Частые ошибки и диагностика 🛠️

- ⚠️ **Ошибка: Команда запускается, но результат «не тот»**
  > Проверьте корректность целевых ID и конкретную подкоманду; чаще всего проблема в несоответствии endpoint и переданных аргументов.
  >
  > ---

- ⚠️ **Ошибка: Неочевидный отказ в автоматизации**
  > Убедитесь, что в CI переданы все обязательные параметры и отключены интерактивные ожидания ввода там, где это необходимо.
  >
  > ---

- ⚠️ **Ошибка: Сложно сравнить результаты между запусками**
  > Сохраняйте выходные артефакты в файл и используйте единый формат вывода для повторяемого анализа.
